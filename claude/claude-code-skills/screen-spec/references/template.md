# Screen spec template and example

Read before writing or checking a screen file. The rules behind each
section are in `SKILL.md` → What each file holds; this file holds the exact
shape and one filled example. Headings, frontmatter keys and column names
are frozen: tests, `frontend` and `ui-test-cases` find sections by them.

Cell rules that are easy to get wrong:

- «Поведение по условиям»: one bold condition per branch, each ending in an
  outcome from the closed set (`SKILL.md` → The outcome of an action). The
  look of a branch is its variant in «Кадр» or in the branch itself
  (`вариант Слот=Своя`), never words about colours or icons.
- «Метод и поля»: response fields as paths from the response root
  (`rooms[].bookings[].is_mine`); request parameters as
  `<operationId>` ← `<parameter>` = `<where the value comes from>`.
- Texts on status rows: «Тексты» is keyed by element and SRS flow
  (`№8 отменить бронь · UC-2 Exc-1`), not by status. Follow the flow to the
  SRS named error and to the status whose error code the operation declares
  for it, and write the flow id beside the code so the reader can check it.
- Empty Разрывы is a table with no rows plus the line «Разрывов нет.».

## Example — S-1 «Расписание» (room booking)

`documentation/ui/screen-specs/S-1-schedule.md`. The product: a coworking's
meeting-room booking. SRS actors A-1 Резидент and A-2 Администратор; rules
BR-2 (бронировать не дальше 14 дней вперёд), BR-3 (резидент отменяет только
свою бронь, администратор — любую), BR-4 (начавшуюся бронь отменить нельзя),
BR-5 (прошедшее время не бронируется). `getSchedule` declares 200, 401, 422,
429, 500; `cancelBooking` declares 204, 401, 403, 404, 409, 429, 500.

  - documentation/ui/frames-register.md

# S-1. Расписание

## Журнал изменений

| Версия | Дата | Изменение | Тип | Кого затрагивает |
|---|---|---|---|---|
| 0.1.0 | 2026-10-04 | первый выпуск | — | — |

## Экран

- **Акторы:** A-1 Резидент — смотрит расписание, открывает бронирование, отменяет свою бронь; A-2 Администратор — то же и видит, чья бронь, и отменяет любую (BR-3).
- **Сценарии:** UC-3 Посмотреть расписание, UC-1 Забронировать переговорную (вход), UC-2 Отменить бронь.
- **Вход:** стартовый экран после входа; из S-2 «Новая бронь» после создания брони и по «Назад»; адрес `/schedule?date=ГГГГ-ММ-ДД`.
- **Ведёт на:** S-2 «Новая бронь» (эл. 4), M1 «Отмена брони» (эл. 5).
- **Узкая ширина:** кадр `20:123`.
- **Фокус:** при входе — эл. 1; после закрытия M1 — эл. 5, из которого он открыт, а если бронь отменена — эл. 4 на её месте; после ошибки в M1 — текст ошибки в M1.

## Загрузка и вызовы

1. Вход на экран, смена даты в эл. 2, «Повторить» в состоянии Error → `getSchedule` (`date` — выбранная дата; при входе — из адреса, без него — «Сегодня»).
2. Подтверждение в M1 (эл. 8) → `cancelBooking` (`bookingId` — бронь, из которой открыт M1).
3. После `204` в ответ 2 → `getSchedule` за ту же дату (из ответа 2 ничего не берёт).

| 3 | переговорная | **Всегда:** название и «до {capacity} человек»; порядок — как в ответе → нет действия | `getSchedule`: `rooms[].name`, `rooms[].capacity` | `16:760` |
| 4 | новая бронь в слоте | **«Слот в прошлом»:** вариант `Слот=Прошёл` → нет действия (BR-5) <br> **Иначе:** вариант `Слот=Свободен` → переход на S-2 с `room_id` и началом слота | `getSchedule`: `rooms[].room_id`; «Слоты дня», «Слот свободен» | `16:770` · `Слот=Свободен`, `Слот=Прошёл` |

Кадр: `17:40` (`S-1 · M1 · Отмена брони`). Открывается: эл. 5.

What the example shows: element names are the action layers without their
prefix (`действие: отменить бронь` → «отменить бронь»), and the nested step's
elements continue the annotation's one numbering (7–9); one element (5) with
four branches by API flag and role; status rows carry the SRS flow that keyed
their text; a rule the API computes cited, not recomputed (`can_cancel`); derived
values defined once and referred to by name; every declared status of both
operations accounted for; no colour, icon, size, hover or backend step in
words; three Разрывы, each with one owner.
