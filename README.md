# dev-pipeline — от идеи до работающего сервиса вместе с Claude

Плагин для Claude Code, который проводит веб-сервис через все этапы разработки:

- требования;
- схема данных;
- API;
- архитектура;
- макеты в Figma;
- ТЗ на экраны;
- тест-кейсы;
- план;
- код с ревью;
- проверка через интерфейс;
- контейнеры и CI.

Вы принимаете решения — Claude делает работу и спрашивает на каждом шаге.

Версия плагина: **1.2.174**

почему пропущено, он скажет сам.

### Итерация

Итерация — один проход по этапам ради одной версии сервиса. У нового проекта первая версия `0.1.0`; у
доработки плагин предлагает следующий номер по тому, что меняется, и спрашивает. Рабочие файлы итерации
лежат в `documentation/plans/<версия>/` и в git не попадают.

Вся работа итерации идёт в одной ветке `iteration/<версия>`, поэтому в `main` всегда лежит последняя
законченная версия:

- плагин создаёт её от `main` в начале итерации, и все этапы делают коммиты в неё; в `main` за итерацию
  не попадает ничего;
- на GitHub отправляется только эта ветка: команду даёт плагин, запускаете её вы, и вы же сливаете ветку в
  `main`;
- следующая итерация начнётся от обновлённого `main`; если прошлая ветка ещё не слита, плагин предупредит.

### Исполнители и сложность

Работу на каждом этапе делают агенты-исполнители — отдельные копии модели, у каждой свои указания. Модель
подбирается под работу: где решать почти нечего, работает модель попроще и подешевле, где ошибка стоит дорого
— самая сильная. На трёх этапах плагин для этого сначала оценивает сложность работы, на остальных исполнитель
один.

| Этап | Как выбирается исполнитель | Модель |
|---|---|---|
| Требования | один исполнитель | Sonnet, high |
| Схема БД, API, архитектура | по сложности документа | низкая — Sonnet, high<br>средняя — Opus, high<br>высокая — Opus, xhigh |
| Макеты в Figma | по виду работы | новые экраны, редизайн, образцы направлений — Opus, high<br>правки и перекраска готовых экранов — Sonnet, medium |
| ТЗ на экраны | один исполнитель | Sonnet, high |
| Тест-кейсы | один исполнитель | Sonnet, medium |
| Сверка документов | один исполнитель | Sonnet, high |
| План | по сложности плана | низкая — Sonnet, high<br>средняя — Opus, high<br>высокая — Opus, xhigh |
| Код с ревью | по сложности каждой задачи | см. «Задачи кода» ниже |
| UI-тестирование | один исполнитель | Sonnet, high |
| Аудит безопасности | один исполнитель | Opus, high |

Решения в требованиях, документах и плане принимает исполнитель этапа, а в файл их печатает отдельный —
Sonnet, low: длинный текст по готовым решениям не требует сильной модели.

Проверки тоже распределены по моделям:

- ревью документа:
  - согласованность и выполнимость — Sonnet, medium;
  - язык проекта и объём — Sonnet, high;
  - замысел, безопасность и попытка опровергнуть документ — Opus, high;
- ревью плана:
  - структура — Sonnet, medium;
  - суждение о задачах — Opus, xhigh;
- ревью кода:
  - каждой задачи — по её сложности (ниже);
  - итоговое ревью всего результата — Opus, high.

**Что такое сложность.** Это не объём и не важность работы, а то, сколько решений остаётся исполнителю.
Длинный документ о простом CRUD — низкая сложность; короткий, где нужно решить, кто к чему получает доступ, —
высокая.

**Документы и план:**

- низкая — одна таблица, одна операция или простой CRUD, где решать нечего;
- средняя — обычная работа одной части системы, или документу предстоит решить вопрос доступа, денег или
  секретов;
- высокая — такой вопрос вместе с переделкой нескольких разделов, или большая связанная работа: много
  сценариев, таблиц и операций со своими правилами.

**Задачи кода.** Каждой задаче плана плагин ставит одну из четырёх сложностей:

| Сложность | Что это за задача | Исполнитель | Ревью задачи |
|---|---|---|---|
| Механическая | одна повторяемая правка: переименование, перенос, значение настройки, перегенерация — сколько бы файлов она ни задела | Haiku, low | отдельного нет: изменения смотрит сам плагин |
| Низкая | всё решено в документах, а в проекте есть похожий код: перенести решение в код | Sonnet, medium | одно ревью на пачку низких задач — Opus, high |
| Средняя | часть решений остаётся исполнителю или ошибка стоит дорого: принять оставшиеся решения и доказать их тестами | Sonnet, high | ревью задачи — Opus, high |
| Высокая | решение открыто, задача задевает несколько частей проекта или ошибку не исправить: спроектировать недостающее в заданных границах и проверить на крайних случаях | Sonnet, high | строгое ревью — Opus, xhigh — и отдельная проверка рисков |

Экраны по макетам при любой сложности пишет отдельный исполнитель для интерфейса — Sonnet, high; ревью — по
сложности задачи.

Сложность задачи плагин определяет по шести признакам:

- осталось ли что-то решать;
- насколько полно задача описана в документах;
- сколько частей проекта она задевает;
- есть ли в проекте похожий код, на который можно опереться;
- чем обойдётся ошибка;
- как доказать результат: прямой проверкой или только с подменой времени, одновременными запросами, сквозным
  прогоном.

Правила:

- задача не ниже средней, если ошибка в ней касается:
  - входа;
  - прав доступа;
  - денег;
  - миграций на существующих данных;
  - секретов;
  - или внешнего контракта;
- такая задача — высокая, если в ней ещё осталось решение или её доказывает только тест одновременных
  запросов (например, деньги списываются под блокировкой строки);
- три дорогих признака сразу — высокая, даже без риска;
- объём — не сложность: тридцать файлов одной правки — механическая задача.

**Если исполнитель не справился**, задача поднимается на уровень выше вместе с отчётом прошлой попытки:
механическая → низкая → средняя → высокая → последний уровень (Sonnet, high). На последнем уровне задача
повторяется, пока попытки что-то дают; потом плагин останавливается и спрашивает вас. Выше механического
уровня модель везде одна и та же: следующий уровень помогает не моделью посильнее, а своими указаниями и
отчётом прошлой попытки.

### Проверки между этапами

Каждый этап опирается на результат предыдущего: код пишется по плану, план — по документам, документы — по
требованиям. Пробел, пропущенный в требованиях, потом обойдётся переделкой кода. Поэтому после этапов
плагин проверяет их результат, прежде чем идти дальше. Проверок пять:

- **Допрос** (`grill-me`) — плагин задаёт неудобные вопросы по требованиям, чтобы не осталось молчаливых
  допущений. На каждый вопрос отвечаете вы. Идёт после идеи и после требований. На первой
  версии его лучше не пропускать.
- **Ревью документа** (`doc-review`) — несколько «рецензентов» с разных сторон (логика, безопасность,
  выполнимость) ищут пробелы. Плагин показывает все замечания сразу и предлагает пройти их по одному —
  решение по каждому ваше. После правок плагин спрашивает, проверить ли ещё раз; кругов будет столько,
  сколько понадобится. Идёт после:
  - требований;
  - схемы БД;
  - API;
  - каждого документа архитектуры;
  - ТЗ на экраны.
- **Сверка документов** (`docs-consistency`) — отдельный этап перед планом: плагин читает все документы вместе
  и проверяет, что у каждого требования есть место в документах, а одно и то же везде называется одинаково.
- **Ревью плана** (`plan-review`) проверяет, что:
  - задачи действительно маленькие;
  - порядок верный;
  - каждый критерий приёмки чем-то покрыт.

  Замечания к плану плагин исправляет сам и проверяет снова, пока план не пройдёт.
- **Ревью кода** (`code-review-unit`, `code-review-full`) — проверяет каждую задачу сразу после неё и весь
  результат в конце.

Допрос, ревью документа и сверку плагин сначала предлагает, а вы выбираете:

- запустить;
- пропустить;
- или остановиться.

Ревью плана и ревью кода идут сами: к этому моменту продуктовые решения уже приняты в документах, и
найденное плагин исправляет сам. Если какого-то решения не хватает, он остановится и спросит.

Замечание, которое идёт против уже записанного решения (например, в требованиях сказано, что лимита запросов с
одного адреса нет), плагин сам не исправляет — ни в ревью, ни в аудите: он показывает это решение и спрашивает,
менять ли его.

Как идёт проверка документа:

```mermaid
flowchart TD
    A[Документ готов] --> Q{Проверить?}
    Q -- пропустить --> N[Следующий этап]
    Q -- остановиться --> X[Пауза до вашего слова]
    Q -- запустить --> G[Допрос — у требований]
    G --> R[Ревью: рецензенты ищут пробелы]
    R --> F{Есть замечания?}
    F -- нет --> N
    F -- да --> D[Вы решаете по каждому]
    D --> P[Плагин правит документ]
    P --> Q2{Проверить ещё раз?}
    Q2 -- да --> R
    Q2 -- нет --> N
    classDef you fill:#7a4a00,stroke:#e0a040,color:#ffffff
    class Q,D,Q2 you
```

Коричневым — шаги, где решаете вы.

Пропуск проверки — нормальный выбор для маленького изменения; плагин сам порекомендует, когда можно пропустить.

**Круги исправлений.** Если проверка что-то нашла, плагин исправляет и проверяет снова, пока проверка не
пройдёт; заранее заданного числа кругов нет. Новый круг запускают только блокирующие замечания, мелкие уходят
в отчёт. Если замечание осталось после исправления, за него берётся исполнитель следующего уровня. В файле
прогресса видно, как идут круги: «Круг 3: закрыто 2, осталось 1».

Плагин остановится и спросит вас:

- когда круги перестали давать результат:
  - вернулось уже исправленное замечание;
  - круг ничего не закрыл;
  - не справился исполнитель последнего уровня;
- или когда нужно ваше решение.

### Выполнение плана

Код пишет плагин (`work`) по готовому плану, задача за задачей.

Путь одной задачи:

```mermaid
flowchart TD
    A[Следующая задача плана] --> B[Исполнитель по сложности]
    B --> T{Рискованная задача?}
    T -- да --> T1[Сначала тесты, они должны упасть]
    T1 --> C[Код задачи]
    T -- нет --> C
    C --> L[Линтер, типы, тесты]
    L -- ошибка --> B
    L -- зелёные --> R[Ревью задачи]
    R -- принято --> K[Коммит]
    R -- мелкие замечания --> M[Механическая правка]
    M --> K
    R -- переделать --> E[Тот же или исполнитель сильнее]
    E --> C
    R -- нужно ваше решение --> U[Вопрос вам]
    U --> W[Решение в документы]
    W --> B
    K --> N{Ещё задачи?}
    N -- да --> A
    N -- нет --> H[Критерии готовности, здоровье кода]
    H --> F[Финальное ревью всего результата]
    F -- замечания --> X[Исправления]
    X --> F
    F -- прошло --> Z[План выполнен]
    classDef you fill:#7a4a00,stroke:#e0a040,color:#ffffff
    class U you
```

Коричневым — шаг, где решаете вы.

**Выполнение идёт само:** ревью, исправления и повторные проверки идут без вопросов к вам. Плагин
останавливается и спрашивает, только когда задача не может пройти:

- в документах не хватает решения;
- ревью нашло ошибку в проектных документах, а не в коде;
- или круги исправлений перестали давать результат.

Тогда плагин напишет в чат:

- что мешает;
- что уже пробовали;
- что вы можете решить.

Ваше решение плагин сам вносит в документы и коммитит, прежде чем продолжить (см. «Решение поменялось по ходу
работы» в разделе [Доработка существующего проекта](#доработка-существующего-проекта)).

Прогон можно оставить на ночь: закончив задачу, плагин сразу берёт следующую и вашего ответа не ждёт.
Случайное или короткое сообщение («ну?», «ты тут?») прогон не останавливает: плагин ответит одной строкой со
счётом и ссылкой на прогресс и продолжит.

**Проверить, а не спросить.** Прежде чем спросить вас о чём-то внутри прогона, плагин смотрит, нельзя ли
узнать ответ, просто что-то запустив, например:

- какой порт у стенда;
- отдаёт ли API поле;
- проходит ли тест без правки;
- дефект это приложения или теста.

Такое он проверяет сам и пишет «решил по проверке: … → …». Спрашивает только о решениях: продукт, объём,
правило, которое документы оставили открытым. На этапах проектирования вопросы задаются намеренно, и это
правило их не касается.

#### Качество кода

Код пишут агенты, и качество держат не на словах:

- **Правила языка.** Каждый исполнитель получает правила своего языка и библиотек — `typescript`, `react`,
  `python` и скиллы библиотек. Плагин подбирает их по стеку проекта и файлам задачи.
- **Автоматические проверки** — после каждой задачи и в CI на каждый push; ошибка возвращает задачу
  исполнителю:
  - линтер с порогами сложности и размера функций и файлов;
  - запрет пустых `catch` и промисов, результат которых никто не проверяет;
  - проверка типов вместе с тестами;
  - границы слоёв;
  - мёртвый код и дубли.
- **Ревью задачи** смотрит то, чего машина не видит: правило, скопированное в другой слой вместо того, чтобы
  взять его из одного места, и ошибки, которые перехватываются и пропадают
  без записи в лог.
- **Тесты:**
  - правила, которые должны держаться на любых входах, проверяются на сотнях случайных значений;
  - тесты бизнес-правил — мутационной проверкой: программа нарочно ломает код и смотрит, заметят ли тесты;
  - защиту от двойного действия доказывает тест двух одновременных запросов к настоящей базе.
- **Сначала тесты** — для задач со входом, правами, деньгами, миграциями на существующих данных или
  секретами и для всех задач высшей сложности: исполнитель сначала пишет только тесты, плагин проверяет, что
  они падают по нужной причине, и только потом исполнитель пишет код.
- **Здоровье кода в конце прогона:** отдельный коммит убирает то, что разрослось за прогон, а итоговое ревью
  проверяет, что код не стал хуже.
- **Зависимости.** CI проверяет их на известные уязвимости отдельной задачей: сначала она только
  предупреждает, обязательной её делают разработчики проекта, когда готовы.

#### Долгий прогон: остановка, продолжение, сжатие контекста

Прогон можно остановить и продолжить без потерь:

- на «стоп», «подожди» или «остановись» прогон останавливается на безопасной границе: плагин сохраняет
  незаконченную работу и останавливает фоновые процессы, которые следят за стендом и тестами;
- если прогон прервался (обрыв связи или сжатие контекста — Claude Code сокращает длинную переписку до
  сводки), любое ваше сообщение возобновит его с того места, где
  он остановился;
- новая сессия ничего сделанного не переделывает и не повторяет уже провалившиеся попытки.

#### Стенд для проверок в браузере

Браузерным тестам в `work`, UI-тестированию и аудиту безопасности нужно запущенное приложение. Как его
поднять, плагин записывает в сам проект — скилл `.claude/skills/verify/`:

- команда запуска и что значит «готов»;
- вход под каждой ролью;
- тестовые данные;
- подвохи окружения.

Скилл пишет первый этап, которому нужен стенд, дальше плагин сам дополняет его. Так каждая следующая сессия
берёт готовое, а не выясняет заново.

### Прогресс долгих этапов

Каждый долгий этап ведёт файл прогресса со страницей, где видно, как идёт работа. У выполнения плана это
`documentation/plans/<версия>/progress.md` рядом с планом. В нём по каждой задаче:

- что делает;
- какой агент её выполняет;
- статус;
- итог ревью.

Строка меняется сразу, как только меняется статус задачи.

Статусы одни и те же во всех файлах прогресса — у задач, экранов, документов, сканеров, исправлений и
стендов:

| Статус | Значит |
|---|---|
| `⏳ ждёт` | ещё не начато |
| `🔄 в работе` | начато: отдано исполнителю, рисуется, пишется, выполняется, исправляется |
| `🔍 ревью`, `🔍 аудит`, `🔍 разбор`, `🔍 проверка` | сделано, идёт проверка — название говорит, какая |
| `✅ готово` | закончено и принято, полоса прогресса считает эти строки |
| `🔁 возвращено: <что>` | отправлено на доработку после проверки |
| `⛔ остановлено: <причина>` | дальше нельзя без решения или недостающего, или не удалось запустить |
| `⏭ пропущено: <почему>` | не нужно, вне объёма или ушло в отчёт |

После двоеточия этап может уточнить шаг (`🔄 в работе: печать`). Исключение одно — отчёт UI-тестирования:
там таблица — это отчёт о дефектах, и у кейса свои итоги (см. ниже).

**Как открыть:** в приложении Claude плагин сам открывает страницу прогресса этапа во встроенном браузере —
у выполнения плана это `progress.html` — и даёт ссылку на неё в чат. На странице:

- полоса прогресса;
- счёт;
- сколько строк в каждом статусе;
- таблица задач.

Страница обновляется сама каждые 5 секунд; её отдаёт локальный сервер, который виден только с вашего
компьютера. В терминальном Claude Code встроенного браузера нет: там ссылка ведёт на файл. Ссылка
повторяется после каждой задачи вместе со счётом — «План: 3 из 6 · progress.html» — и при каждой остановке.

Так выглядит страница прогресса:

Все задачи весят одинаково, процент округляется вниз, поэтому 100% появится только после последней задачи.

### UI-тестирование

Тест-кейсы плагин пишет заранее, вместе с дизайном, а на этапе UI-тестирования прогоняет их на запущенном
приложении. `ui-test-cases` работает в двух режимах:

- **Запись** — после ТЗ на экраны: критерии приёмки из требований становятся пронумерованными кейсами с
  шагами и ожидаемыми текстами.
- **Прогон** — после этапа «Код с ревью»: кейсы превращаются в Playwright-тесты и прогоняются на запущенном
  приложении в два прохода — сначала весь набор, потом разбор упавших. Заодно экраны сверяются с макетами на
  каждой ширине из реестра макетов: страница не должна прокручиваться вбок (UX-74).

Как идёт прогон:

```mermaid
flowchart TD
    A[Приложение запущено] --> P1[Проход 1: каждый кейс один раз]
    P1 --> P2[Проход 2: разбор упавших]
    P2 --> W{Почему упал?}
    W -- ошибка в тесте --> FT[Тест чинится]
    FT --> RR[Кейс перезапускается]
    RR -- снова упал --> W
    RR -- прошёл --> Z[Итог прогона]
    W -- дефект приложения, расхождение с макетом, пробел в ТЗ --> REP[Запись в отчёт]
    REP --> Z
    Z --> Q{Есть дефекты?}
    Q -- да --> PL[План исправлений — по вашему решению]
    Q -- нет --> N[Аудит безопасности]
    classDef you fill:#7a4a00,stroke:#e0a040,color:#ffffff
    class PL you
```

Коричневым — шаг, где решаете вы.

Дефекты плагин сам не исправляет: если вы решите, он составит по ним отдельный план.

<details>
<summary><b>Как выглядит тест-кейс</b></summary>

Кейс читает человек (тестировщик, аналитик, вы), а агент прогона превращает его в автотест. Поэтому у кейса два
слоя: тело — человеческим языком, всё техническое — в строке «Трассировка» под ним.

> **TC-7. Резидент не может отменить бронь, которая уже началась**
>
> **Проверяет:** UC-2 AC-Exc-2 · BR-4
> **Кто:** резидент · **Экран:** Расписание переговорных (S-2), окно «Отмена брони»
> **Подготовка:** резидент вошёл; у него бронь «Байкал», начавшаяся 10 минут назад
>
> | # | Действие | Что должно быть |
> |---|---|---|
> | 1 | Открыть расписание на сегодня | бронь «Байкал» отмечена как своя |
> | 2 | Выбрать свою бронь «Байкал» | открылось окно «Отмена брони» |
> | 3 | Выбрать «Отменить бронь» | в окне текст «Бронь уже началась, отменить нельзя»; в расписании бронь осталась |
>
> <sub>Трассировка: кадр 12:160 · шаг 2 → эл. 11; шаг 3 → эл. 3 (M2), `cancelBooking` → 409 BOOKING_STARTED</sub>

Шаги — действия по подписям, которые видны на экране; ожидаемое — то, что видно глазами, с точными
текстами и настоящими датами. Кадры, номера элементов, вызовы API и коды ответов — только в трассировке:
по ней агент находит элементы на странице, подменяет ответы
сервера и сверяет экран с макетом.

Если ТЗ на экран, макет или API поменялись, ссылки в трассировке кейсов перепроверяются; что можно,
плагин исправляет сам, а к вам попадает только то, чего больше нет (элемент, на который ссылается кейс,
удалён).

</details>

<details>
<summary><b>Прогон пользовательских тестов: два прохода, полосы, статусы</b></summary>

Перед стартом плагин даёт ссылку на страницу `test-run.html`, перед вторым проходом — ещё раз.

1. **Проход 1 — весь набор до 100%.** Каждый кейс пишется и прогоняется один раз: прошёл, не прошёл или
   заблокирован. Тесты в этом проходе плагин не чинит —
   сначала нужна полная картина. Если кейсы проверяются в
   нескольких режимах (например, два способа входа), каждая пара «кейс × режим» считается отдельно.
2. **Проход 2 — разбор упавших.** Каждый не прошедший кейс разбирается:
   - ошибка в тесте — плагин чинит тест и перезапускает кейс, круг за кругом, пока каждая починка что-то
     меняет;
   - дефект приложения, расхождение с макетом или пробел в ТЗ — записываются как есть.

**Главная полоса — доля успешных кейсов**, а не выполненных: полоса «выполнено 94%» при трети упавших
выглядела бы почти готовой. Кейсы, которые нельзя автоматизировать, в процент не входят: успешно 18 из 23 —
это 78%. Полоса растёт в первом проходе и после каждого круга перезапуска, когда исправленные тесты начинают
проходить. Под ней — «Проверено: 24 из 24 · успешно 18 · не прошли 4 · заблокировано 1 · не автоматизированы
1»; «не прошли» — только настоящие падения.

**Перезапуск — со своей полосой.** Пока кейсы перезапускаются, основная полоса стоит на месте, а у
перезапуска свой блок с полосой и итогом.

Итог («Verdict») появляется только после второго прохода: `PASS`, `DEFECTS` или `BLOCKED`.

  - или `⏭ не автоматизирован` (автотестом на общем стенде честно не проверить: нужен отказ хранилища,

- Итог второго прохода:
  - `✅ тест исправлен, прошёл`;
  - `⛔ тест не удалось исправить`;

  - или `❓ пробел в ТЗ` (ТЗ этого не описывает).

`✅ прошёл после исправления теста`.

поднимает несколько одинаковых стендов (не больше четырёх) и делит тесты между ними; если стенд проекта
ещё нельзя копировать, он перед прогоном предложит сделать это отдельным коммитом. В отчёте написано, сколько
стендов взято и что ограничило; после прогона они убираются, чужие окружения (`dev`, `demo`) не трогаются.

### Аудит безопасности

Ревью кода в `work` смотрят только то, что изменил очередной план. Раз за итерацию, перед сборкой релиза,
`security-audit` проверяет приложение целиком. Запустить его можно и в любой момент: «проверь безопасность».

1. **Сканеры по всему коду и всей истории git** (через Docker, ничего не ставится на компьютер):
   - уязвимые версии зависимостей (`osv-scanner`);
   - ключи и пароли в файлах и старых коммитах (`gitleaks`);
   - опасные шаблоны кода по OWASP (`semgrep`).
2. **Матрица доступа** из документов: каждая операция API — кто её может вызывать по требованиям и чьи
   данные она трогает.
3. **Проверка по областям**: агент на Opus проходит каждую операцию от входа запроса до базы
   данных:
   - проверяются ли права;
   - нельзя ли получить чужие данные, подменив id;
   - проверяется ли ввод;
   - не уходит ли лишнее в ответе и в ошибках.

   Отдельно проверяются настройки всего приложения: сессии, cookie, CORS, лимиты, конфигурация.
4. **Перепроверка**: второй проход пытается опровергнуть каждую серьёзную находку, и ложные
   срабатывания отсеиваются.

По каждой находке P0/P1 плагин спросит:

- исправить;
- принять риск (с вашей причиной);
- или отложить.

Исправления идут обычным планом и `work`, после них аудит перепроверяет только исправленное. Пока открыта
находка P0, этап «Контейнеры» не соберёт релиз, если вы не скажете «собирать всё равно». Сами Docker-образы
проверяются сканером `trivy` при сборке релиза. Сканеры качают базы уязвимостей из интернета; за
корпоративным прокси плагин берёт настройки прокси с машины, а если сеть недоступна, сканер помечается «не
запускался: сеть», и аудит идёт дальше.

### Эксплуатационная документация

`DEPLOY.md` говорит, как систему запустить. Что делать с ней потом, говорит
`documentation/operations/operations.md`:

- где посмотреть:
  - кто отменил бронь;
  - отработала ли ночная очистка;
  - почему не ушло письмо;
- что делать, когда растёт очередь.

Плагин пишет его после сборки образов и кладёт в релиз как `OPERATIONS.md` рядом с `DEPLOY.md`.

<details>
<summary><b>Что внутри документа</b></summary>

Документ один для двух читателей: тех, кто эксплуатирует систему, и разработчиков на дежурстве. В каждой
строке — задача человеческими словами и отдельным столбцом «Где в системе»: таблица, файл, операция API.
Разделы:

- доступы;
- журналы:
  - что в записи;
  - кто пишет;
  - сколько хранится;
  - как посмотреть;
- готовые SQL-запросы только для чтения;
- события в логах с фильтрами;
- проверки и метрики;
- фоновые процессы;
- тревоги;
- типовые операции;
- разбор проблем по симптомам.

Всё берётся из схемы, архитектуры, требований и кода — ничего не придумывается. Если журнал по требованиям
должен видеть администратор, а увидеть его можно только SQL-запросом, документ так и пишет: «только SQL —
экрана нет», и этот пробел попадает в отчёт этапа. Каждый запрос и каждую команду плагин прогоняет на тестовом
стенде на настоящих записях, а тест в проекте проверяет все запросы документа на тестовой базе: переименуют
колонку — упадёт сборка, а не дежурный ночью.

**Обязательные журналы.** Журналы, которые система обязана вести по закону, регламенту или требованиям
безопасности (обработка персональных данных, согласия, запросы субъектов, доступ к ПДн, аудит действий), идут
отдельным разделом «Обязательные журналы»:

- основание;
- срок хранения по основанию и в системе;
- кто может смотреть.

Если такой журнал требуется, а в системе его нет, или срок короче положенного, — это первая строка отчёта
этапа.

</details>

### Конец итерации

Когда пройден последний этап итерации (или последний из тех, что вы не пропустили), плагин закрывает её сам:

- пересобирает сайт документации;
- пишет итог версии `plans/<версия>/summary.md` — это и есть закрытие;
- ставит метку `v<версия>` в git — снимок документации и кода; с ним следующая итерация сравнивает,
  что изменилось;
- запускает разбор сессий для плагина (`/dev-pipeline:reflect`, см. ниже);
- убирает рабочие файлы закрытой итерации (см. ниже) и даёт команду, чтобы отправить ветку.

Если вы остановили работу раньше последнего этапа, а версию всё равно выпускаете, напишите «итог» — плагин
закроет итерацию так же.

**Уборка.** После итога плагин удаляет рабочие файлы закрытой итерации, чтобы не копить архив:

- план;
- ревью плана;
- файлы прогресса;
- отчёты прогонов и аудита;
- служебные файлы.

Остаётся только `summary.md` — цифры итерации. Документы проекта (требования, API, архитектура, ТЗ,
тест-кейсы) не трогаются. Перед удалением плагин переносит в документы то, что было записано только в
рабочих файлах, —
например, принятые риски из отчёта аудита уходят в решения архитектуры. Папка `plans/` не хранится в git,
удалённое не вернуть, поэтому плагин показывает список с размерами и спрашивает один раз. Лишние файлы в
`documentation/` — которых нет в реестре и на которые никто не ссылается — он только показывает и спрашивает
по каждому.

### Разбор сессий для плагина

В конце каждой итерации, без вопроса, плагин запускает `reflect`: перечитывает сессии этого проекта за
итерацию и записывает, где сработал не так сам плагин, а не проект. Например:

- вы поправляли этап («а где ссылка?», «прогресс не обновляется»);
- этап нарушил правило своего скилла;
- правило потерялось после сжатия контекста;
- сессия долго выясняла то, что должно быть в правилах.

Итог дописывается в `~/.claude/dev-pipeline-feedback/<проект>.md` — вне репозитория проекта, в git ничего
не попадает. У каждой находки ваши слова как доказательство, скилл и правило и что предлагается поменять.
Плагин сам себя не правит: файл читает тот, кто ведёт плагин. Запустить вручную в любой момент:
`/dev-pipeline:reflect` или «разбери сессии для плагина».

</details><!-- /раздел -->

Делается один раз, после [установки плагина](#установка).

2. **Обновите плагин.** Команда откроет вкладку Marketplaces — выберите в ней `dev-pipeline-marketplace` и
   пункт **Update marketplace**:

   ```text
   /plugin marketplace update dev-pipeline-marketplace
   ```

3. **Включите новую версию в открытой сессии** (в новых сессиях она работает сразу):

   ```text
   /reload-plugins
   ```

Или то же самое в терминале, после чего перезапустите Claude Code:

```bash
claude plugin marketplace update dev-pipeline-marketplace
```

```bash
claude plugin update dev-pipeline@dev-pipeline-marketplace
```

**Чтобы обновления приходили сами:** `/plugin` → вкладка Marketplaces → `dev-pipeline-marketplace` →
**Enable auto-update**. Claude Code будет сам проверять новые версии после начала сессии.

**Проекты после обновления.** Новая версия иногда меняет, какими должны быть файлы проекта. Изменения бывают
двух видов, и у каждого своя команда:

- **Документы** — `/dev-pipeline:upgrade-docs`:
  - появляется новый документ;
  - новый раздел в нём;
  - новое правило для текста, который плагин уже написал.
- **Код и настройки проекта** — `/dev-pipeline:upgrade-code`:
  - автоматические проверки качества кода;
  - скилл запуска стенда;
  - подключение плагина для всех, кто открывает репозиторий.

Команды разделены, потому что документы правит аналитик и правка ничего не ломает, а изменение кода лучше
отдать разработчику: плагин прогоняет проверки проекта до и после каждого изменения, и поведение приложения
не меняется.

В начале сессии плагин одной строкой скажет, каких изменений в проекте ещё нет и какой командой их сделать.
Каждая команда объясняет свои изменения и по каждому спрашивает:

- сделать сейчас;
- не нужно этому проекту;
- или позже.

Выбранное делается по коммиту на изменение: в ветке открытой итерации, если она идёт, иначе в отдельной ветке
— `docs/plugin-<версия>` для документов, `chore/plugin-<версия>` для кода. Версию плагина команда записывает
в `documentation/.dev-pipeline.json`, когда изменений «на потом» не осталось ни у одной из двух. Без вашего
ответа ничего не меняется.

</details><!-- /раздел -->

<a id="доработка-существующего-проекта"></a>
<details>
<summary><h2>Доработка существующего проекта</h2></summary>

Когда сервис уже есть, новая фича идёт тем же путём, но документы не пишутся заново — правятся на месте.
Начинайте с идеи, как и в первый раз:

```text
/dev-pipeline:brainstorm Добавить отмену брони: резидент может отменить свою бронь не позже чем за час.
```

`brainstorm` дополнит существующие бизнес-требования (новые пункты получают следующие свободные номера)
и уточнит то, что в идее не сказано:

- кто ещё может отменять;
- что происходит с отменённой бронью;
- кого уведомить.

Если идея уже описана точно — с критериями приёмки и границами, — он сам это заметит,
обойдётся парой вопросов и предложит перейти к требованиям.

Дальше плагин ведёт по тем же этапам и затрагивает только то, что меняется: каждое изменение в документе
помечается как «ломает», «добавляет» или «уточняет», и следующие этапы предлагаются только для тех
документов, которых оно касается.

### Новый вид интерфейса без новых функций

Требования не меняются, начинайте прямо с макетов:

```text
/dev-pipeline:ui-design Новое визуальное направление для всего интерфейса.
```

`ui-design` предложит 2–3 направления (цвета, шрифт, скругления, плотность) — образцы появятся на
странице «🎨 Направления» в Figma, вы выберете. Затем спросит, как применить выбранное:

- **перекрасить** — те же макеты, меняется только вид: структура экранов, тексты и номера кадров
  остаются, прежний вид сохраняется в архиве файла. Если экраны уже сделаны в коде, следующим будет
  план с задачей на тему оформления — экраны подхватят её без переделки;
- **нарисовать заново на отдельной странице** — все экраны рисуются заново в новом направлении,
  прежние макеты остаются рядом нетронутыми. Потом обновляются ТЗ на экраны (у новых кадров новые
  номера) и тест-кейсы, затем план.

Если какой-то экран нужно перестроить, а не только перекрасить, это редизайн: он идёт через ТЗ на
экран, как новый.

### Решение поменялось по ходу работы

Бывает, что решение меняется уже после того, как документ с ним написан:
- вы ответили на остановку в `work`;
- передумали посреди прогона («давай по-другому»);
- при просмотре макетов сказали «убери это поле»;
- прогон тестов показал, что неверно ТЗ, а не код;
- оказалось, что библиотека не умеет так, как записано.

Напоминать про документацию не нужно — плагин сам:

1. записывает изменение в раздел «Изменённые решения» — в отчёте и файле прогресса;
2. находит документ, которому решение принадлежит (требования, API, схема БД, архитектура, ТЗ на экран,
   тест-кейсы), и все документы, которые его повторяют, и правит их на месте;
3. сразу коммитит эти правки отдельным коммитом `docs: решение изменено — …`, **не меняя версию**:
   номер версии и строки журнала появятся при следующей простановке версий, и туда попадут все такие
   изменения;
4. продолжает работу уже по новому тексту. Код, который успели написать по старому решению, переделывается
   отдельным коммитом, а финальное ревью проверяет, что ни одно решение не осталось только в коде.

Если правка требует нового проектирования (например, меняется весь ход сценария), плагин остановится и
предложит запустить нужный этап.

</details><!-- /раздел -->
