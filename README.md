# dev-pipeline — от идеи до работающего сервиса вместе с Claude

> Плагин для Claude Code, который проводит веб-сервис через все этапы разработки: требования, схема
> данных, API, архитектура, макеты в Figma, ТЗ на экраны, тест-кейсы, план, код с ревью, проверка через
> интерфейс, контейнеры и CI. Вы принимаете решения — Claude делает работу и спрашивает на каждом шаге.

Версия плагина: **1.2.168**

## Что получится в итоге

- **Комплект документации** — понятный и связанный: требования (SRS), схема базы данных, контракт API,
  архитектура, макеты в Figma, ТЗ на каждый экран, пользовательские тест-кейсы. Документы пишутся в формате
  Markdown (`.md`) в папке `documentation/`, а плагин сам собирает из них статичный сайт
  (`documentation/_web-docs/`) с меню, поиском и ссылками между документами. Открыть сайт:
  `/dev-pipeline:open-docs` или просто «открой сайт документации».
- **Работающий код** — бэкенд и фронтенд, каждый кусок прошёл ревью перед коммитом.
- **Проверка через интерфейс** — Playwright-тесты по тест-кейсам, прогнанные на запущенном приложении.
- **Контейнеры и CI** — docker-compose для тестов, разработки и продакшена; для эксплуатации — папка
  выпуска `release/<версия>/` с архивом образов и двумя инструкциями: `DEPLOY.md` (как запустить) и
  `OPERATIONS.md` (где что смотреть потом); проверки на каждый push.

Структура документации:

```text
documentation/
├── _web-docs/         сайт документации — собирается сам
├── requirements/      требования: бизнес-требования, SRS, пожелания к интерфейсу
├── db/                схема базы данных, миграции, страница на каждую таблицу
├── api/               OpenAPI-спецификация
├── architecture/      архитектура: основа, доменная модель, сценарии по областям
├── ui/                реестр макетов, ТЗ на экраны, тест-кейсы на пользовательские сценарии
├── project-map/       карта проекта: где какой документ и где код
├── deploy/            инструкция по запуску (deploy.md)
└── operations/        эксплуатационная документация (operations.md)
```

## Что нужно подготовить

### 1. Figma — для макетов

Плагин рисует макеты экранов прямо в Figma, а потом пишет по ним ТЗ для фронтенда.

Нужен **платный аккаунт Figma** (Professional, Organization или Enterprise) с доступом **Full**. С доступом
**Dev** тоже получится, но файл для макетов должен лежать в разделе «Черновики» (Drafts) вашего Figma, а не
в проекте команды: файлы команды с доступом Dev открываются только для чтения.

Если у сервиса нет интерфейса, Figma не нужна — дизайн-этапы пропускаются.

### 2. MCP-серверы

| Сервер | Зачем | Что сделать |
|---|---|---|
| **Figma** | рисовать макеты, читать их для ТЗ и для проверки экранов | один раз войти в аккаунт — см. [Как подключить Figma](#как-подключить-figma) |
| **Context7** | брать актуальную документацию библиотек, когда пишется код | ничего, работает сразу |

Без входа в Figma этапы с макетами остановятся и попросят подключить Figma.

#### Как подключить Figma

Делается один раз, после [установки плагина](#установка).

1. **Войдите в нужный аккаунт Figma в браузере** (figma.com). Подключится тот аккаунт, который сейчас открыт
   в браузере, — если у вас их несколько, сначала выйдите из лишнего.
2. **Откройте Claude Code** в терминале в любой папке:

   ```bash
   claude
   ```

3. **Выполните в чате команду** `/mcp`:

   ```text
   /mcp
   ```

   Откроется список подключений. Сервер Figma из плагина называется `plugin:dev-pipeline:figma` и
   помечен как требующий входа (`needs authentication`).
4. **Выберите его стрелками, нажмите Enter и выберите Authenticate.** Откроется браузер со страницей Figma.
   Если браузер не открылся, Claude Code покажет ссылку — скопируйте её и откройте вручную.
5. **На странице Figma нажмите Allow access** — так вы разрешаете Claude работать с вашими файлами.
6. **Вернитесь в терминал.** Появится сообщение `Authentication successful. Connected to figma`, а в
   списке `/mcp` у сервера будет статус `connected`. Список закрывается клавишей Esc.

### 3. Программы на компьютере

| Программа | Зачем |
|---|---|
| **Claude Code 2.1.293+** | с этой версии механические задачи (переименования, значения настроек, мелкие исправления по ревью) выполняет быстрая и дешёвая модель Haiku 5.5; в старых версиях вместо неё запускается Haiku 4.5, которую на коде не проверяли. Версию покажет `claude --version`; приложение Claude обновляет её само |
| **Git** | история изменений, каждый шаг — коммит |
| **Python 3** | на нём работают хуки плагина: страницы прогресса, пересборка сайта документации и страниц таблиц БД, проверка проекта при старте сессии; ещё — поиск по базе стилей при выборе визуального направления |
| **D2** | схемы в документах (архитектура, схема БД) |
| **PlantUML** | диаграммы последовательности для сложных сценариев |
| **Node.js 22+** | проверка и разбивка контракта API, страница API на сайте документации; сервис на TypeScript; тесты через браузер |
| **uv** | зависимости сервиса — только если он на Python |
| **Docker** (Docker Desktop или Docker Engine) | локальная база данных, контейнеры, сборка образов, сканеры аудита |
| **Браузер для тестов** (Chromium от Playwright) | проверка приложения через интерфейс |

Если D2 или PlantUML не установлены, документы всё равно пишутся, но вместо картинки схемы останется
только её исходный текст — плагин об этом скажет. PlantUML можно заменить Docker'ом: плагин сам
запустит его в контейнере.

<details>
<summary><b>macOS</b></summary>

**1. Homebrew** — менеджер программ для macOS. Если уже стоит (`brew --version` печатает версию), пропустите.

```bash
/bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"
```

В конце установщик покажет две-три команды «Next steps» — выполните их, чтобы `brew` стал доступен.

**2. Git, D2, PlantUML, Node.js, Python 3:**

```bash
brew install git d2 plantuml node python
```

**3. Docker Desktop:**

```bash
brew install --cask docker
```

Откройте Docker Desktop из «Программ» один раз и дождитесь, пока он запустится (значок кита в строке меню).

**4. Python и uv** — только если сервис будет на Python:

```bash
brew install uv
```

**5. Браузер для тестов через интерфейс:**

```bash
npx playwright install chromium
```

<details>
<summary><b>Linux (Ubuntu, Debian)</b></summary>

Через `apt` ставятся только Git, curl и PlantUML: D2 в стандартных репозиториях нет, а Docker и Node.js там
устаревших версий, поэтому для них — официальные способы установки.

**1. Git, curl, PlantUML, Python 3:**

```bash
sudo apt update && sudo apt install -y git curl plantuml python3
```

**2. D2:**

```bash
curl -fsSL https://d2lang.com/install.sh | sh -s --
```

**3. Docker Engine** (вместе с ним ставится buildx для сборки образов):

```bash
curl -fsSL https://get.docker.com | sh
```

Чтобы запускать Docker без `sudo`, добавьте себя в группу `docker`:

```bash
sudo usermod -aG docker $USER
```

Затем выйдите из системы и войдите снова (или перезагрузитесь), чтобы это вступило в силу.

**4. Node.js 22** — через nvm:

```bash
curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.8/install.sh | bash
```

Откройте новое окно терминала и поставьте Node.js:

```bash
nvm install 22
```

**5. Python и uv** — только если сервис будет на Python:

```bash
curl -LsSf https://astral.sh/uv/install.sh | sh
```

**6. Браузер для тестов через интерфейс** (вместе с системными библиотеками, которые ему нужны):


На Fedora и Arch вместо шага 1 — `sudo dnf install git curl plantuml` или `sudo pacman -S git curl plantuml`;
остальные шаги те же.

</details>

<details>
<summary><b>Windows (через WSL 2)</b></summary>

Плагин работает в Linux-окружении внутри Windows — WSL 2 с Ubuntu. Все программы ставятся в Ubuntu,
а Docker — как Docker Desktop для Windows, который отдаёт Docker в Ubuntu.

Нужна Windows 11 или Windows 10 версии 2004 и новее (узнать: Win+R → `winver`). В BIOS/UEFI должна быть
включена виртуализация (Intel VT-x или AMD-V) — на большинстве компьютеров она включена; проверить:
Диспетчер задач → Производительность → ЦП → «Виртуализация: Включено».

**1. WSL 2 и Ubuntu.** Откройте PowerShell от имени администратора (Пуск → PowerShell → правой кнопкой →
«Запуск от имени администратора») и выполните:

```powershell
wsl --install
```

Перезагрузите компьютер. После перезагрузки откроется окно Ubuntu (если не открылось — найдите Ubuntu в
меню Пуск). Придумайте имя пользователя и пароль для Linux: они не связаны с учётной записью Windows,
пароль понадобится для команд с `sudo`.

Если WSL уже стоял, обновите его и проверьте, что Ubuntu работает на версии 2:

```powershell
wsl --update
```

```powershell
wsl -l -v
```

В колонке VERSION должно быть `2`. Если там `1`:

```powershell
wsl --set-version Ubuntu 2
```

**2. Docker Desktop для Windows** — ставится в Windows, не в Ubuntu. Скачайте
[Docker Desktop](https://docs.docker.com/desktop/setup/install/windows-install/) или в PowerShell:

```powershell
winget install -e --id Docker.DockerDesktop
```

Запустите Docker Desktop и в его настройках проверьте:
- Settings → General → включено «Use the WSL 2 based engine»;
- Settings → Resources → WSL integration → включён переключатель напротив Ubuntu → Apply & restart.

Docker Desktop должен быть запущен, когда плагин собирает образы или поднимает контейнеры.

Дальше всё — в окне Ubuntu (Пуск → Ubuntu, или вкладка Ubuntu в Windows Terminal).

**3. Git, curl, PlantUML, Python 3:**

```bash
sudo apt update && sudo apt install -y git curl plantuml python3
```

**4. D2:**

```bash
curl -fsSL https://d2lang.com/install.sh | sh -s --
```

**5. Node.js 22** — через nvm:

```bash
curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.8/install.sh | bash
```

Закройте и снова откройте окно Ubuntu и поставьте Node.js:

```bash
nvm install 22
```

Проверьте, что используется Node.js из Ubuntu, а не из Windows — путь должен начинаться с `/home/`:

```bash
which node
```

**6. Python и uv** — только если сервис будет на Python:

```bash
curl -LsSf https://astral.sh/uv/install.sh | sh
```

**7. Браузер для тестов через интерфейс** (вместе с системными библиотеками, которые ему нужны):

```bash
npx playwright install --with-deps chromium
```

**8. Папка для проектов.** Держите проекты внутри Ubuntu, а не на диске `C:` (`/mnt/c/...`): там работа с
файлами в разы медленнее, и сборка с тестами заметно тормозит.

```bash
mkdir -p ~/projects && cd ~/projects
```

Открыть эту папку в Проводнике Windows можно командой `explorer.exe .`, а в VS Code (с расширением WSL) —
`code .`.

## Установка

В Claude Code (в чате) выполните две команды:

```text
/plugin marketplace add Idontlikedrinkpivo/web-dev-pipeline-claude-plugin
```

```text
/plugin install dev-pipeline@dev-pipeline-marketplace
```

Или то же самое в терминале:

```bash
claude plugin marketplace add Idontlikedrinkpivo/web-dev-pipeline-claude-plugin
```

```bash
claude plugin install dev-pipeline@dev-pipeline-marketplace
```

Затем:

1. **Перезапустите Claude Code** — так он увидит скиллы и агентов плагина.
2. **Подключите Figma** — по шагам в разделе [Как подключить Figma](#как-подключить-figma).

### Обновление до новой версии

Номер последней версии указан в начале этого README («Версия плагина»).

В Claude Code (в чате):

1. **Узнайте, какая версия стоит у вас:**

   ```text
   /plugin list
   ```

2. **Обновите плагин.** Команда откроет вкладку Marketplaces — выберите в ней `dev-pipeline-marketplace` и
   пункт **Update marketplace**:

   ```text
   /plugin marketplace update dev-pipeline-marketplace
   ```

3. **Включите новую версию в открытой сессии** (в новых сессиях она работает сразу):

   ```text
   /reload-plugins
   ```

Или то же самое в терминале, после чего перезапустите Claude Code:

```bash
claude plugin marketplace update dev-pipeline-marketplace
```

```bash
claude plugin update dev-pipeline@dev-pipeline-marketplace
```

**Чтобы обновления приходили сами:** `/plugin` → вкладка Marketplaces → `dev-pipeline-marketplace` →
**Enable auto-update**. Claude Code будет сам проверять новые версии после начала сессии.

**Проекты после обновления.** Новая версия иногда меняет, какими должны быть файлы проекта: появляется
новый документ, новый раздел в нём, новое правило для текста, который плагин уже написал. В начале сессии и
после `/clear` плагин сам проверяет, чего в проекте ещё нет, и говорит об этом одной-двумя фразами — даже
когда итерация не идёт. Чтобы привести проект к новой версии, напишите `/dev-pipeline:upgrade-docs`: плагин
объяснит каждое изменение и по каждому спросит — сделать сейчас, не нужно этому проекту или позже.
Выбранное он делает по коммиту на изменение: в ветке открытой итерации, если она идёт, иначе в отдельной
ветке `docs/plugin-<версия>`. Версию плагина он записывает в `documentation/.dev-pipeline.json`, когда не
осталось изменений «на потом». Без вашего ответа он ничего не меняет.

## Быстрый старт: первый проект

1. Создайте пустую папку для проекта и откройте её в Claude Code.
2. Опишите идею. Подходит любой формат — пара абзацев, заметка, тикет, письмо заказчика:

   ```text
   /dev-pipeline:brainstorm Хочу сервис бронирования переговорных для коворкинга.
   Резиденты бронируют комнату на время, администратор закрывает комнату на обслуживание.
   ```

   Если требования уже понятны и записаны, начните сразу с SRS:

   ```text
   /dev-pipeline:srs-writer <ваше описание или путь к файлу с ним>
   ```

3. Отвечайте на вопросы. Claude задаёт их по одному и предлагает варианты с рекомендацией. Ответ — обычное
   сообщение: буква варианта или свой текст.
4. После каждого этапа Claude показывает результат и спрашивает, что дальше: **запустить** следующий этап,
   **пропустить** проверку или **остановиться**. Можно остановиться в любой момент и вернуться позже.
5. В новой сессии напишите `/dev-pipeline:pipeline где я` — плагин по файлам на диске поймёт, где вы
   остановились, и предложит следующий шаг.

## Как устроен процесс

После требований работа идёт двумя ветками — бэкенд и дизайн — и они встречаются перед планом. Порядок
выбираете вы, плагин спросит один раз: обе параллельно (вопросы помечены [Бэкенд] / [Дизайн]),
последовательно в любом порядке, только одну (вторую ведёт другой человек или позже) или остановиться.
ТЗ на экраны в любом случае ждут API.

```mermaid
flowchart TD
    A[Идея] --> B[Требования]
    subgraph backend [Бэкенд]
        C[Схема БД] --> D[API] --> E[Архитектура] --> F[Каркас проекта]
    end
    subgraph design [Дизайн]
        G[Макеты в Figma] --> H[ТЗ на экраны] --> I[Тест-кейсы]
    end
    B --> C
    B --> G
    F --> J[Сверка документов]
    I --> J
    J --> K[План] --> L[Код с ревью] --> M[Проверка через интерфейс] --> S[Аудит безопасности] --> N[Контейнеры] --> P[Эксплуатация] --> O[CI]
```

| Этап | Скилл | Что происходит | Проверка после этапа | Что делаете вы | Что появляется |
|---|---|---|---|---|---|
| Идея | `brainstorm` | разбираем идею: цель, пользователи, границы | допрос `grill-me` | отвечаете на вопросы | бизнес-требования |
| Требования | `srs-writer` | пишет SRS: требования, сценарии, правила, критерии приёмки | допрос `grill-me` → ревью `doc-review` | отвечаете, принимаете | `requirements/srs/`: `srs.md` и файлы групп |
| Схема БД | `db-schema-design` | проектирует таблицы и первую миграцию; по каждой таблице — свой документ с полями и связями | ревью `doc-review` | смотрите, задаёте вопросы | `db/schema.md`, `db/migrations/`, `db/tables/` |
| API | `openapi-spec-generator` | описывает контракт API | ревью `doc-review` | — | `api/openapi.yaml` и файлы операций и схем |
| Архитектура | `clean-architecture-design` | основа, доменная модель, сценарии; предлагает стек | ревью `doc-review` каждого документа | выбираете стек из вариантов | `architecture/` |
| Каркас | `repo-scaffold` | создаёт пустой запускаемый проект по архитектуре, с линтерами и проверками качества | — | — | код каркаса, карта проекта |
| Макеты | `ui-design` | предлагает 2–3 визуальных направления образцами в Figma, рисует экраны по требованиям в выбранном; умеет перекрасить готовые макеты | — (макеты смотрите вы сами) | даёте ссылку на файл Figma, выбираете направление, смотрите макеты | макеты, `ui/frames-register.md` |
| ТЗ на экраны | `screen-spec` | ТЗ на фронтенд по каждому экрану | ревью `doc-review` | — | `ui/screen-specs/` |
| Тест-кейсы | `ui-test-cases` | пользовательские сценарии проверки, по файлу на раздел | — | — | `ui/test-cases/` |

Нет интерфейса — дизайн-ветка пропускается. Нет базы данных — пропускается схема. Плагин сам скажет, что и
почему пропущено.

### Проверки между этапами

Где какая проверка — в колонке «Проверка после этапа». Перед допросом, ревью документа и сверкой Claude
спрашивает: запустить, пропустить или остановиться. Ревью плана и ревью кода идут сами: к этому моменту все
продуктовые решения уже приняты в документах, и найденное — работа самого плагина.

- **Допрос** (`grill-me`) — Claude задаёт неудобные вопросы по требованиям, чтобы не осталось молчаливых
  допущений. На каждый вопрос отвечаете вы. Лучше не пропускать на первой версии. У SRS допрос всегда идёт
  раньше ревью, а что прошло, записывается в сообщение коммита SRS — так это знает и новая сессия.
- **Ревью документа** (`doc-review`) — несколько «рецензентов» с разных сторон (логика, безопасность,
  выполнимость) ищут пробелы. Плагин показывает все замечания сразу и предлагает пройти их по одному —
  решение по каждому ваше. После правок спрашивает, проверить ли ещё раз; кругов сколько понадобится.
- **Сверка комплекта** (`docs-consistency`) — все документы вместе: у каждого требования есть место в
  документах, одно и то же везде называется одинаково.
- **Ревью плана** (`plan-review`) — задачи действительно маленькие, порядок верный, каждый критерий приёмки
  чем-то покрыт. Замечания к плану плагин исправляет сам, кругами до прохождения.
- **Ревью кода** (`code-review-unit`, `code-review-full`) — каждой задачи сразу после неё и всего результата
  в конце.

Пропуск проверки — нормальный выбор для маленького изменения; плагин сам порекомендует, когда можно пропустить.

**Выполнение плана (`work`) идёт само:** ревью, исправления и повторные проверки крутятся без вопросов.
Работа останавливается и спрашивает вас, только когда задача не может пройти: в документах не хватает
решения, ревью упёрлось в проект, а не в код, или круги исправлений перестали давать результат. Тогда в чате
будет сказано, что мешает, что уже пробовали и что вы можете решить. Ваше решение плагин сам вносит в
документы и коммитит, прежде чем продолжить (см. [Решение поменялось по ходу
работы](#решение-поменялось-по-ходу-работы)).

Прогон можно оставить на ночь: каждый шаг заканчивается тем, что следующая задача уже запущена. Случайное или
короткое сообщение («ну?», «ты тут?») прогон не останавливает: плагин ответит одной строкой со счётом и
ссылкой на прогресс и продолжит. Остановить можно словами «стоп», «подожди» или «остановись».

<details>
<summary><b>Повтор до полного прохождения: как идут круги исправлений</b></summary>

Если проверка что-то нашла, исправление и повторная проверка идут кругами, пока проверка не пройдёт, — без
заранее заданного числа кругов. Чтобы это не стоило лишнего:

- повторная проверка читает только то, что изменило последнее исправление, и ещё открытые замечания, а не
  всю работу заново (исключение — ревью документа: правка в одном разделе может противоречить другому,
  поэтому он перечитывается целиком, но уже решённые замечания не поднимаются снова);
- исправляющий получает историю — что уже пробовали, чтобы не повторять;
- исполнитель уровнем выше подключается, только если замечание пережило исправление: для документов это
  более сильная модель, для кода — новая попытка с отчётом прошлой;
- круги крутятся только из-за блокирующих замечаний, мелкие уходят в отчёт.

Плагин остановится и спросит вас не после N кругов, а когда круги перестали давать результат: вернулось уже
исправленное замечание, круг ничего не закрыл, последний уровень исполнителя не справился — или когда нужно
ваше решение. В файле прогресса видно, как идут круги: «Круг 3: закрыто 2, осталось 1».

Если два исправления подряд упали на одной проверке и оба исходили из одного допущения («элемент просто
долго появляется», «эта база от этого кода»), третье не пишется: сначала допущение проверяется тем, что
дало бы другой результат, будь оно ложным (куда реально уходит запрос, какие миграции записаны в базе).
Только потом — следующее исправление или следующий исполнитель, уже с правильной целью.

Если задача кода дошла до последнего исполнителя (`impl-critical`) и проверка показала, что неверен сам
подход, следующий круг — два подхода сразу. Плагин называет два разных подхода одной фразой каждый, два
исполнителя пробуют их с одного и того же коммита (параллельно в отдельных копиях репозитория, если тесты не
делят базу или порт). Победителя выбирают тесты и проверка задачи, при равенстве — ревью; от проигравшего
ничего не берётся. Случай редкий, поэтому двойная цена почти не видна. В проектировании документов такой
«арены» нет: там она в 2–2,5 раза дороже при спорном выигрыше — судья, читающий два документа, не замечает
пробелов победителя, а тестов у документа нет.

</details>

### Качество кода

Код пишут агенты, и качество держат не на словах:

- **Правила языка.** Каждый исполнитель получает правила своего языка и библиотек — `typescript`, `react`,
  `python` и скиллы библиотек. Плагин подбирает их по стеку проекта и файлам задачи.
- **Автоматические проверки** в каждой части проекта (бэкенд, фронтенд): линтер с порогами сложности и
  размера функций и файлов, запрет пустых `catch` и неподтверждённых промисов, проверка типов вместе с
  тестами, границы слоёв, мёртвый код и дубли. `work` запускает их после каждой задачи — ошибка возвращает
  задачу исполнителю, — CI повторяет на каждый push.
- **Ревью задачи** смотрит то, чего машина не видит: правило, скопированное в другой слой вместо того, чтобы
  взять его из одного места, и проглоченные ошибки без следа в логе.
- **Тесты.** Правила, которые должны держаться на любых входах (формат, диапазон, «кто правит — тот видит»),
  проверяются тестами свойств на сотнях случайных значений, а тесты бизнес-правил — мутационной проверкой:
  программа нарочно ломает код и смотрит, заметят ли тесты. Защиту от двойного действия (блокировка строки,
  условное обновление, уникальный ключ, ключ идемпотентности) доказывает тест двух одновременных запросов к
  настоящей базе, каждый со своим соединением; защита без такого теста — замечание ревью.
- **Сначала тесты — для рискованных задач.** Задачи с входом, правами, деньгами, миграциями на существующих
  данных или секретами и все задачи высшей сложности идут в два прохода: исполнитель сначала пишет только
  тесты, и сессия сама проверяет, что они падают по нужной причине; потом он же пишет код, не ослабляя
  проверок.
- **Здоровье кода в конце прогона.** `work` сравнивает дубли, сложность и размеры с началом, отдельный коммит
  убирает то, что разрослось, не меняя поведения, а итоговое ревью проверяет, что код не стал хуже.
- **Зависимости.** CI проверяет их на известные уязвимости отдельной задачей: сначала она только
  предупреждает, обязательной её делает команда, когда готова.

В существующий проект проверки добавляет `/dev-pipeline:upgrade-docs`: старые нарушения записываются
списком и исправляются постепенно, новые не допускаются.

### Следить за работой

Пока выполняется план, плагин ведёт файл прогресса `documentation/plans/<версия>/progress.md` рядом с
планом. В нём каждая задача: что делает, какой агент её выполняет, статус и итог ревью. Строка меняется
сразу, как только меняется статус задачи.

Статусы одни и те же во всех файлах прогресса — у задач, экранов, документов, сканеров, исправлений и
стендов:

| Статус | Значит |
|---|---|
| `⏳ ждёт` | ещё не начато |
| `🔄 в работе` | начато: отдано исполнителю, рисуется, пишется, выполняется, исправляется |
| `🔍 проверка` | сделано, идёт проверка: ревью, аудит, разбор |
| `✅ готово` | закончено и принято, полоса прогресса считает эти строки |
| `🔁 возвращено: <что>` | отправлено на доработку после проверки |
| `⛔ остановлено: <причина>` | дальше нельзя без решения или недостающего, или не удалось запустить |
| `⏭ пропущено: <почему>` | не нужно, вне объёма или ушло в отчёт |

После двоеточия этап может уточнить шаг (`🔄 в работе: печать`, `🔍 проверка: ревью`). Исключение одно —
отчёт о прогоне тест-кейсов: там таблица — это отчёт о дефектах, и у кейса свои итоги (см. ниже).

**Как открыть:** в приложении Claude плагин сам открывает страницу прогресса этапа во встроенном браузере —
у выполнения плана это `progress.html` — и даёт ссылку на неё в чат. На странице полоса прогресса, счёт,
сколько строк в каждом статусе и таблица задач. Страница обновляется сама каждые 5 секунд. Чтобы встроенный
браузер её обновлял, плагин отдаёт страницы через маленький локальный сервер (`http://127.0.0.1:…`, виден
только с вашего компьютера) и останавливает его в конце итерации. В терминальном Claude Code встроенного
браузера нет: там ссылка ведёт на файл, а обычный браузер обновляет его сам. Ссылка повторяется после каждой
задачи вместе со счётом — «План: 3 из 6 · progress.html» — и при каждой остановке.

У каждого файла прогресса своя страница рядом с ним, с тем же именем: `progress-design.md` →
`progress-design.html`, `test-run.md` → `test-run.html`. Источник — сами файлы в Markdown: их правят агенты,
а страницу после каждой правки пересобирает хук плагина, в том числе когда правку делает субагент.

### Тест-кейсы и проверка через интерфейс

`ui-test-cases` работает в двух режимах. **Запись** — после ТЗ на экраны: критерии приёмки из требований
становятся пронумерованными кейсами с шагами и ожидаемыми текстами. **Прогон** — после `work`: кейсы
превращаются в Playwright-тесты и прогоняются на запущенном приложении в два прохода — сначала весь набор,
потом разбор упавших. Заодно экраны сверяются с макетами на каждой ширине из реестра макетов: страница не
должна прокручиваться вбок (UX-74). Дефекты плагин не исправляет: по ним составляется отдельный план.

<details>
<summary><b>Как выглядит тест-кейс</b></summary>

Кейс читает человек (тестировщик, аналитик, вы) и превращает в автотест агент прогона. Поэтому у кейса два
слоя: тело — человеческим языком, всё техническое — в строке «Трассировка» под ним.

> **TC-7. Резидент не может отменить бронь, которая уже началась**
>
> **Проверяет:** UC-2 AC-Exc-2 · BR-4
> **Кто:** резидент · **Экран:** Расписание переговорных (S-1), окно «Отмена брони»
> **Подготовка:** резидент вошёл; у него бронь «Байкал», начавшаяся 10 минут назад
>
> | # | Действие | Что должно быть |
> |---|---|---|
> | 1 | Открыть расписание на сегодня | бронь «Байкал» отмечена как своя |
> | 2 | Выбрать свою бронь «Байкал» | открылось окно «Отмена брони» |
> | 3 | Выбрать «Отменить бронь» | в окне текст «Бронь уже началась, отменить нельзя»; в расписании бронь осталась |
>
> <sub>Трассировка: кадр 12:160 · шаг 2 → эл. 11; шаг 3 → эл. 3 (M2), `cancelBooking` → 409 BOOKING_STARTED</sub>

Шаги — действия по подписям, которые видны на экране; ожидаемое — то, что видно глазами, с точными
текстами и настоящими датами. Кадры, номера элементов, вызовы API и коды ответов — только в трассировке:
по ней агент строит локаторы, моки и сверку с макетом.

**Трассировка проверяется в двух точках.** Если кейс поправили, а ТЗ на экран, макет или API поменялись,
ссылки в трассировке могут указывать на то, чего уже нет. Скрипт `check_trace.py` сверяет каждую ссылку с
текущими документами — шаг есть в кейсе, элемент в ТЗ, кадр в ТЗ или реестре макетов, вызов и код ответа в
OpenAPI — и запускается:

- **в начале `screen-spec`**, если тест-кейсы уже есть: битую трассировку переписывает автор тест-кейсов по
  текущему ТЗ (для экранов, чьё ТЗ переписывается в этом прогоне, — после него);
- **в сверке документов перед планом**: исправление идёт само, без вопросов, затем повторная проверка; к
  вам попадает только то, что не исправить механически (элемента, на который ссылается кейс, больше нет).

</details>

<details>
<summary><b>Скилл запуска стенда в проекте</b></summary>

У каждого проекта своя кухня запуска: какой compose, когда стенд действительно готов, как войти под нужной
ролью, где тестовые данные, какие подвохи у окружения (прокси, старая сборка, база от другой ветки). Чтобы
каждая сессия не выясняла это заново, в самом проекте лежит скилл `.claude/skills/verify/`: команда запуска,
что значит «готов», скрипт проверки стенда, вход по ролям, куда складывать доказательства, как убрать за
собой, раздел «Подвохи» и карта функций.

- Пишет его первый этап, которому нужен запущенный стенд, — браузерные тесты в `work`, прогон тест-кейсов
  или аудит безопасности, — если скилла ещё нет. Этап Docker (`deploy-topology`) каждую итерацию сверяет его
  с изменившимся приложением.
- Скилл обязательно прогоняется один раз целиком (запуск, проверка, одна функция в браузере, уборка) — без
  этого он черновик.
- Скрипт проверки (`doctor.sh`) ничего не меняет и ловит самые дорогие поломки до запуска тестов: не тот
  стенд на порту, нет готовности, база мигрирована из другого кода, сборка старше коммита.
- Прогон UI-тестов, браузерные тесты в `work` и аудит безопасности первым делом читают этот скилл и
  запускают проверку; новый подвох сессия дописывает в него, а не только в отчёт.
- Пробные прогоны складывают результаты отдельно и не затирают отчёты и скриншоты владельца.

</details>

<details>
<summary><b>Прогон пользовательских тестов: два прохода, полосы, статусы</b></summary>

Перед стартом Claude даёт ссылку на страницу `test-run.html`, перед вторым проходом — ещё раз.

1. **Проход 1 — весь набор до 100%.** Каждый кейс пишется и прогоняется один раз: прошёл, не прошёл или
   заблокирован. Тесты в этом проходе не чинятся — сначала полная картина. Если кейсы проверяются в
   нескольких режимах (например, два способа входа), каждая пара «кейс × режим» считается отдельно.
   Исключение — общая поломка: если подряд падают кейсы из-за одного общего помощника (вход под ролью,
   подготовка данных), проход останавливается, помощник чинится, и эти кейсы перезапускаются.
2. **Проход 2 — разбор упавших.** Каждый не прошедший кейс разбирается: ошибка в тесте — тест чинится и
   кейс перезапускается, круг за кругом, пока каждая починка что-то меняет; дефект приложения, расхождение с
   макетом или пробел в ТЗ — записываются как есть.

**Главная полоса — доля успешных кейсов**, а не выполненных: полоса «выполнено 94%» при трети упавших
выглядела бы почти готовой. Кейсы, которые нельзя автоматизировать, в процент не входят: успешно 18 из 23 —
это 78%. Полоса растёт и в первом проходе, и с каждым кругом перезапуска, когда исправленные тесты начинают
проходить. Под ней — «Проверено: 24 из 24 · успешно 18 · не прошли 4 · заблокировано 1 · не автоматизированы
1»; «не прошли» — только настоящие падения.

**Любой перезапуск — со своей полосой.** Пока кейсы перезапускаются, основная полоса стоит на месте. Чтобы это
не выглядело зависанием, у перезапуска свой блок: что исправили, какие кейсы перезапускаются, своя полоса,
«Перезапущено: N из M», а в конце — итог. Пока он идёт, под основной полосой строка «Сейчас: перезапуск, круг
N — x из y». Основная полоса назад не откатывается.

Итог («Verdict») появляется только после второго прохода: `PASS`, `DEFECTS` или `BLOCKED`.

>
> ```text
> ██████████████████████████████████████████████████████████████████████████████░░░░░░░░░░░░░░░░░░░░░░ 78%
> ```
>
> Проверено: 24 из 24 · успешно 18 · не прошли 4 · заблокировано 1 · не автоматизированы 1

**Статусы кейса.** Первый проход: `⏳ ждёт` → `🔄 в работе` → `✅ прошёл`, `❌ не прошёл`,
`⛔ заблокирован` (не хватает того, что можно добавить, например тестового входа) или `⏭ не автоматизирован`
(автотестом на общем стенде честно не проверить: нужен отказ хранилища, перезапуск с другой настройкой —
такие кейсы перечисляются под итогом в списке «Проверить вручную» с шагами). Кейс, прошедший после починки
теста, в таблице первого прохода становится `✅ прошёл после исправления теста`. Второй проход:
`⏳ ждёт` → `🔍 проверка` → `✅ тест исправлен, прошёл`, `⛔ тест не удалось исправить`,
`❌ дефект приложения` (приложение расходится с ТЗ), `🖼 расхождение с макетом` (экран не совпадает с
макетом) или `❓ пробел в ТЗ` (ТЗ этого не описывает).

**Проверка экрана.** На каждой ширине из реестра макетов прогон смотрит, что страница не прокручивается вбок
(UX-74); нарушение попадает в список «Проверка экрана» отчёта как дефект приложения.

**Параллельный прогон.** Тесты, которые делят один стенд (одну базу, одно хранилище, одни права
пользователей), идут по одному: два потока на одном стенде мешают друг другу. Ускорение даёт не число
потоков, а число стендов: несколько одинаковых копий, у каждой своя база и своя часть файлов тестов.

- Тестовый стенд с самого начала пишется так, чтобы его можно было копировать: порты и адреса — из
  переменных, без фиксированных имён контейнеров. Скрипт проекта `scripts/e2e-stands.sh up N` поднимает N
  копий из уже собранных образов, `down` убирает.
- Если стенд проекта ещё нельзя копировать, а машина тянет несколько стендов, плагин перед прогоном сам
  предложит сделать его копируемым — это механическая правка, отдельным коммитом — и прогнать параллельно,
  или идти на одном стенде.
- Сколько стендов, прогон измеряет, а не угадывает: число файлов, производительные ядра минус одно,
  свободная память Docker и машины, не больше четырёх. В отчёте написано, сколько стендов взято и что
  ограничило («3 стенда: ядра»).
- Каждый файл тестов сам готовит свои данные и не рассчитывает на то, что оставил другой файл.
- Отчёт один, как и при одном стенде: `test-run.md` для прогона тест-кейсов, раздел в `progress.md` для
  браузерных тестов внутри `work`. В нём одна полоса на все стенды и строка на каждый стенд.
- Тест, упавший по таймауту под нагрузкой, перед разбором перезапускается в одиночку.
- В CI то же: задача e2e делится на шарды по файлам, у каждого свой стенд.
- После прогона стенды, которые он поднял, убираются вместе с фоновыми «следилками»; образы остаются, чужие
  окружения (`dev`, `demo`) не трогаются. В конце отчёта — строка, сколько стендов убрано.

</details>

### Аудит безопасности

Ревью кода в `work` смотрят только то, что изменил очередной план. Раз за итерацию, перед сборкой релиза,
`security-audit` проверяет приложение целиком. Запустить его можно и в любой момент: «проверь безопасность».

1. **Сканеры по всему коду и всей истории git** (через Docker, ничего не ставится на компьютер):
   уязвимые версии зависимостей (`osv-scanner`), ключи и пароли в файлах и старых коммитах (`gitleaks`),
   опасные шаблоны кода по OWASP (`semgrep`).
2. **Матрица доступа** из документов: каждая операция API — кто её может вызывать по требованиям и чьи
   данные она трогает.
3. **Проверка по областям**: агент на Opus проходит каждую операцию от маршрута до базы — проверяются ли
   права, нельзя ли получить чужие данные, подменив id, проверяется ли ввод, не уходит ли лишнее в ответе и в
   ошибках. Отдельно — настройки всего приложения: сессии, cookie, CORS, лимиты, конфигурация.
4. **Перепроверка**: второй проход пытается опровергнуть каждую серьёзную находку — ложные срабатывания
   отсеиваются.

<details>
<summary><b>Находки, релиз и сканеры</b></summary>

По каждой находке P0/P1 плагин спросит: исправить, принять риск (с вашей причиной) или отложить. Находка,
которая идёт против уже записанного решения (например, «предела по адресу нет» в требованиях), по умолчанию
не исправляется никогда — ни в аудите, ни в ревью документов, кода и плана: плагин покажет это решение и
спросит, менять ли его. Исправления идут обычным планом и `work`, после них аудит перепроверяет только
исправленное. Пока открыта находка P0, `deploy-topology` не соберёт релиз, если вы не скажете «собирать всё
равно». Сами Docker-образы проверяются сканером `trivy` при сборке релиза.

Сканеры качают свои базы уязвимостей из интернета. За корпоративным прокси плагин передаёт им настройки
прокси с машины, заранее проверяет доступность источников, хранит базу trivy в томе Docker между прогонами и,
если скачивание встало, переключается на запасной источник; не помогло — сканер помечается «не запускался:
сеть», а аудит идёт дальше.

</details>

### Эксплуатационная документация

`DEPLOY.md` говорит, как систему запустить. Что делать с ней потом — где посмотреть, кто отменил бронь,
отработала ли ночная очистка, почему не ушло письмо, что делать, когда растёт очередь, — говорит
`documentation/operations/operations.md`. Плагин пишет его после сборки образов и кладёт в релиз как
`OPERATIONS.md` рядом с `DEPLOY.md`.

<details>
<summary><b>Что внутри документа</b></summary>

Документ один для двух читателей: тех, кто эксплуатирует систему, и разработчиков на дежурстве. В каждой
строке — задача человеческими словами и отдельным столбцом «Где в системе»: таблица, файл, операция API.
Разделы: доступы, журналы (что в записи, кто пишет, сколько хранится, как посмотреть), готовые SQL-запросы
только для чтения, события в логах с фильтрами, проверки и метрики, фоновые процессы, тревоги, типовые
операции, разбор проблем по симптомам.

Всё берётся из схемы, архитектуры, требований и кода — ничего не придумывается. Если журнал по требованиям
должен видеть администратор, а увидеть его можно только SQL-запросом, документ так и пишет: «только SQL —
экрана нет», и этот пробел попадает в отчёт этапа. Каждый запрос и каждая команда прогоняются на тестовом
стенде на настоящих записях, а тест в проекте проверяет все запросы документа на тестовой базе: переименуют
колонку — упадёт сборка, а не дежурный ночью.

**Обязательные журналы.** Журналы, которые система обязана вести по закону, регламенту или требованиям безопасности (обработка
персональных данных, согласия, запросы субъектов, доступ к ПДн, аудит действий), идут отдельным разделом
«Обязательные журналы»: основание, срок хранения по основанию и в системе, кто может смотреть. Если такой
журнал требуется, а в системе его нет, или срок короче положенного, — это первая строка отчёта этапа.

</details>

- поиск по тексту и по номеру: «FR-12» сразу открывает требование;
- схемы на своих местах, контракт API — страницей в привычном интерфейсе Swagger: операции по разделам, схемы
  запросов и ответов, примеры. Только для чтения, работает без интернета (при сборке нужен Node.js);
- журнал изменений каждого документа свёрнут — раскрывается по клику, не мешает читать сам документ;
- светлая и тёмная тема, удобный вид на телефоне.

Сайт лежит в `documentation/_web-docs/` и коммитится в git: кто клонирует репозиторий, получает его без
сборки. Коммит документов дожидается пересборки и забирает изменения сайта с собой, поэтому сайт в любом
коммите совпадает с документами этого коммита. Пересборка занимает около секунды, меняет только страницы
изменённых документов и общие файлы меню и поиска, а страницу API — только если менялся контракт. В других
репозиториях, где просто есть папка `documentation/`, сайт сам не появляется; отказаться от него в своём
проекте можно через `/dev-pipeline:upgrade-docs` («не нужно этому проекту»).

</details>

**Как открыть:** в приложении Claude напишите `/dev-pipeline:open-docs` или просто «открой сайт» — плагин
дождётся пересборки, если она идёт, откроет свежий сайт во встроенном браузере и даст ссылку в чат. Если
сайта ещё нет, команда сначала соберёт его. «Закрой сайт» останавливает локальный сервер, через который
встроенный браузер показывает сайт (`http://127.0.0.1:…`, виден только с вашего компьютера). В терминале или
без Claude откройте файл в обычном браузере: `open documentation/_web-docs/index.html` или двойным щелчком по
`index.html` в Finder.

Документы остаются в Markdown: сайт — только их вид, его пересобирают, а не правят. Публикует сайт только сам
пользователь.

### Конец итерации

Вся работа итерации идёт в одной ветке `iteration/<версия>`. Плагин создаёт её от `main`, когда открывается
итерация, и все этапы коммитят туда; в `main` за итерацию не попадает ничего. Пушится только эта ветка —
плагин даёт команду, запускаете вы, — и вы сами сливаете её в `main` на GitHub. Следующая итерация начнётся
от обновлённого `main`; если прошлая ветка ещё не слита, плагин предупредит.

Когда пройден последний этап итерации (или последний из тех, что вы не пропустили), плагин закрывает её сам:

- пересобирает сайт документации;
- пишет итог версии `plans/<версия>/summary.md` — это и есть закрытие;
- ставит метку `v<версия>` в git — снимок документации и кода, от которого считается следующая итерация;
- запускает разбор сессий для плагина (`/dev-pipeline:reflect`, см. ниже);
- убирает рабочие файлы закрытой итерации (см. ниже) и даёт команду, чтобы отправить ветку.

Если вы остановили пайплайн раньше, а версию всё равно выпускаете, напишите «итог» — плагин закроет итерацию
так же.

**Уборка.** После итога плагин удаляет рабочие файлы закрытой итерации, чтобы не копить архив: план, ревью
плана, файлы прогресса, отчёты прогонов и аудита, служебные файлы в `.git/pipeline-work/`. Остаётся только
`summary.md` — цифры итерации. Контрактные документы (требования, API, архитектура, ТЗ, тест-кейсы) не
трогаются. Перед удалением то, что жило только в рабочем файле, переносится в свой документ — например,
принятые риски из отчёта аудита уходят в решения архитектуры. Папка `plans/` не хранится в git, удалённое не
вернуть, поэтому плагин показывает список с размерами и спрашивает один раз. Лишние файлы в `documentation/` —
которых нет в реестре и на которые никто не ссылается — он только показывает и спрашивает по каждому.

### Долгий прогон: остановка, продолжение, сжатие контекста

Git и файл прогресса знают, что сделано. Но в голове прервавшейся сессии остаётся то, чего там нет: какие
исправления открытого замечания уже пробовали и почему не вышло, незакоммиченный diff исполнителя, какие
стенды и следилки запущены, какие решения приняты по ходу и ещё не попали в документы. Поэтому `work`, прогон
UI-тестов и аудит ведут рядом с файлом прогресса короткую записку `resume.md` и обновляют её после каждого
пункта.

- На «стоп» прогон останавливается на безопасной границе: незакоммиченное сохраняется патчем в
  `.git/pipeline-work/` (без коммитов `wip:` — правило «одна задача — один коммит» не ломается), следилки
  снимаются, записка обновляется.
- Новая сессия (или та же после сжатия контекста) сначала читает записку и сверяет каждое её утверждение с
  git, рабочим деревом и Docker: где они расходятся, верит реальности. Ничего сделанного не переделывает и не
  повторяет уже провалившиеся попытки. Если прогон прервался (обрыв связи, сжатие контекста), любое ваше
  сообщение возобновит его с того места, где он остановился.

**Напоминание после сжатия контекста.** В долгой сессии Claude Code периодически сжимает переписку в краткую
сводку, и правила прочитанных раньше скиллов из неё выпадают. Плагин ставит хук на старт сессии, её
продолжение, `/clear` и сжатие контекста:

- если в проекте есть открытая итерация (`documentation/plans/<версия>/` без `summary.md`), хук добавляет в
  контекст несколько строк: какая итерация, какой этап шёл последним (по файлам прогресса), просьбу заново
  прочитать `pipeline` и скилл этапа и самые забываемые правила;
- в начале сессии и после `/clear` он одной строкой говорит, каких изменений формата плагина в проекте ещё
  нет (см. [Обновление до новой версии](#обновление-до-новой-версии));
- в остальных случаях молчит.

Хук ничего не меняет и не блокирует — только напоминает; новую версию плагина в уже открытую сессию он не
приносит, для этого нужен перезапуск.

**Проверить, а не спросить.** Внутри прогона перед вопросом вам сессия сортирует его: если ответ — факт,
который можно увидеть, запустив что-то (какой порт у стенда, отдаёт ли API поле, проходит ли тест без
правки, дефект приложения или теста), она проверяет сама и пишет «решил по проверке: … → …». Спрашивает
только о решениях: продукт, объём, правило, которое документы оставили открытым. Вопросы на этапах
проектирования это не трогает — там они задаются намеренно.

### Разбор сессий для плагина

В конце каждой итерации, без вопроса, плагин запускает `reflect`: перечитывает сессии этого проекта за
итерацию и записывает, где сработал не так сам плагин, а не проект. Например: вы поправляли этап («а где
ссылка?», «прогресс не обновляется»), этап нарушил правило своего скилла, правило потерялось после сжатия
контекста, сессия долго выясняла то, что должно быть в правилах. У каждой находки — ваши слова как
доказательство, скилл и правило, которых она касается, и что предлагается поменять.

- Переписку читает скрипт, который сжимает каждую сессию до ваших реплик, ответов и запущенных этапов;
  по одному агенту-рецензенту (Sonnet) на сессию, только сессии этого проекта.
- Итог дописывается в `~/.claude/dev-pipeline-feedback/<проект>.md` — вне репозитория проекта, в git ничего
  не попадает. Каждая итерация — новый раздел с датой, старые не переписываются.
- Плагин сам себя не правит: файл читает тот, кто ведёт плагин, и решает, что брать.
- Запустить вручную в любой момент: `/dev-pipeline:reflect` или «разбери сессии для плагина».

## Доработка существующего проекта

Когда сервис уже есть, новая фича идёт тем же путём, но документы не пишутся заново — правятся на месте.
Начинайте с идеи, как и в первый раз:

```text
/dev-pipeline:brainstorm Добавить отмену брони: резидент может отменить свою бронь не позже чем за час.
```

`brainstorm` дополнит существующие бизнес-требования (новые пункты получают следующие свободные номера)
и уточнит то, что в идее не сказано: кто ещё может отменять, что происходит с отменённой бронью, кого
уведомить. Если идея уже описана точно — с критериями приёмки и границами, — он сам это заметит,
обойдётся парой вопросов и предложит перейти к требованиям.

Когда изменение маленькое и уже сформулировано как требование, можно сразу начать с `srs-writer`:

```text
/dev-pipeline:srs-writer Срок отмены брони меняется с часа на 30 минут.
```

Дальше плагин ведёт по тем же этапам и затрагивает только то, что меняется: каждое изменение в документе
помечается как «ломает», «добавляет» или «уточняет», и следующие этапы предлагаются только для тех
документов, которых оно касается.

<details>
<summary><b>Новый вид интерфейса без новых функций</b></summary>

Требования не меняются, начинайте прямо с макетов:

```text
/dev-pipeline:ui-design Новое визуальное направление для всего интерфейса.
```

`ui-design` предложит 2–3 направления (цвета, шрифт, скругления, плотность) — образцы появятся на
странице «🎨 Направления» в Figma, вы выберете. Затем спросит, как применить выбранное:

- **перекрасить** — те же макеты, меняется только вид: структура экранов, тексты и номера кадров
  остаются, прежний вид сохраняется в архиве файла. Если экраны уже сделаны в коде, следующим будет
  план с задачей на тему оформления — экраны подхватят её без переделки;
- **нарисовать заново на отдельной странице** — все экраны рисуются заново в новом направлении,
  прежние макеты остаются рядом нетронутыми. Потом обновляются ТЗ на экраны (у новых кадров новые
  номера) и тест-кейсы, затем план.

Если какой-то экран нужно перестроить, а не только перекрасить, это редизайн: он идёт через ТЗ на
экран, как новый.

</details>

### Решение поменялось по ходу работы

Бывает, что решение меняется уже после того, как документ с ним написан:
- вы ответили на остановку в `work`;
- передумали посреди прогона («давай по-другому»);
- при просмотре макетов сказали «убери это поле»;
- прогон тестов показал, что неверно ТЗ, а не код;
- оказалось, что библиотека не умеет так, как записано.

Напоминать про документацию не нужно — плагин сам:

1. записывает изменение в раздел «Изменённые решения» — в отчёте и файле прогресса;
2. находит документ, которому решение принадлежит (требования, API, схема БД, архитектура, ТЗ на экран,
   тест-кейсы), и все документы, которые его повторяют, и правит их на месте;
3. сразу коммитит эти правки отдельным коммитом `docs: решение изменено — …`, **не меняя версию**:
   номер версии и строки журнала появятся при следующей простановке версий, и туда попадут все такие
   изменения;
4. продолжает работу уже по новому тексту. Код, который успели написать по старому решению, переделывается
   отдельным коммитом, а финальное ревью проверяет, что ни одно решение не осталось только в коде.

Если правка требует нового проектирования (например, меняется весь ход сценария), плагин остановится и
предложит запустить нужный этап.

### Версии сервиса и документов

У сервиса один номер версии вида `1.4.2`:

| Часть | Когда растёт |
|---|---|
| **первая** (1.x.x) | крупная новая возможность — решаете вы |
| **вторая** (x.4.x) | новая функциональность |
| **третья** (x.x.2) | только исправления |

До первого выпуска версии начинаются с `0.` (первая работа — `0.1.0`). У каждой версии своя папка
`plans/<версия>/` (она живёт только на вашем компьютере, в git не попадает) и своя ветка — см.
[Конец итерации](#конец-итерации).

У каждого документа в начале есть журнал изменений: что поменялось, в какой версии и как —
**ломает** (нужно переделать зависимое), **добавляет** (новое) или **уточняет** (та же суть другими словами).

Каждый документ коммитится сразу, как только его этап закончен (проверки пройдены или пропущены), до вопроса
о следующем этапе, — и так же, если вы остановились на вопросе о проверке или о следующем этапе. SRS, схема
БД с миграцией, API, архитектура, ТЗ на экраны коммитятся с версией и строками журнала (`docs: SRS 2.1.1`),
реестр кадров и тест-кейсы — обычным коммитом. Следующий этап и следующий человек в команде начинают от
коммита.

<details>
<summary><b>Работа командой: дизайнер и аналитик параллельно</b></summary>

Этапы ветки дизайна можно отдать другим людям, а самому в это время вести бэкенд. У каждого свой
компьютер и свой Claude Code с этим плагином, а ветка одна на всех — ветка итерации.

В начале итерации, если у продукта есть экраны, плагин один раз спрашивает, кто ведёт дизайн: **всё делаем
сами** (макеты рисует плагин) или **дизайнер с плагином** на своём компьютере (ему сразу передаются макеты,
бэкенд идёт параллельно). От ответа зависят порядок веток, первый вопрос этапа макетов и кому отдаются ТЗ
на экраны и тест-кейсы. Ответ записывается в реестр кадров, и в следующих итерациях плагин его не
переспрашивает, а только напоминает.

| Кто | Этапы | Пишет только в | Может начать, когда в ветке есть |
|---|---|---|---|
| Вы | требования, схема БД, API, архитектура, каркас, затем план и всё дальше | своё | — |
| Дизайнер | макеты (`ui-design`), тест-кейсы (`ui-test-cases`) | `ui/frames-register.md` и Figma; `ui/test-cases/` | макеты — SRS; тест-кейсы — ТЗ на экраны |
| Аналитик | ТЗ на экраны (`screen-spec`) | `ui/screen-specs/` | макеты и API |

Как это идёт:

1. После требований плагин спросит, какую ветку делать дальше. Выберите «Только бэкенд — дизайн ведёт другой
   человек» и скажите, кому что. Плагин даст вам команду push ветки итерации и готовый текст для каждого: как
   поставить плагин, переключиться на ветку и что запустить.
2. Вы сразу продолжаете бэкенд и пушите каждый готовый документ, чтобы другие его подтянули.
3. Каждый пишет только в свою папку, поэтому коммиты не пересекаются: перед каждым push хватает
   `git pull --rebase`. Номер версии у всех один — он берётся из имени ветки. Если дизайнеру или аналитику
   нужно поменять требования или API, они не правят их сами: плагин подготовит текст-просьбу для вас.
4. Закончив, человек присылает строку «готово и запушено». Ваш плагин подтянет ветку, проверит, что
   тронута только своя папка и ревью ТЗ пройдено, и скажет, кто теперь может начинать.
5. Когда всё отданное готово, идёт сверка документов и дальше план — как обычно.

«Где я» читает ветку итерации на GitHub: что уже сделано и кто кого ждёт.

</details>

Самые сложные документы и планы (деньги, безопасность, изменения через несколько областей) пишет Opus 5.5 с
повышенным усилием (xhigh): на них он не хуже Fable, а стоит меньше; задачи кода выполняет Sonnet,
механические — Haiku.

Каждой задаче плана выставляется сложность, и от неё зависит исполнитель. Задача, которая касается входа,
прав доступа, денег, миграций на существующих данных, секретов или внешнего контракта, всегда не ниже
средней, а если деньги или доступ решаются при одновременных запросах (блокировка строки, гонка за ключ
идемпотентности) — получает высшую, даже когда все шаги расписаны в архитектуре.

**Дизайн — встроены из открытых проектов** (см. [Благодарности](#благодарности)); каждое их правило сведено с
`ux-patterns` и носит его номер `UX-n`, поэтому противоречий между ними нет.

| Скилл | Что делает | Как вызывается |
|---|---|---|
| `/dev-pipeline:ui-ux-pro-max` | база стилей, палитр, шрифтов с кириллицей и шаблонов лендингов — из неё собираются варианты визуального направления | подключает плагин; можно и вам: «подбери палитру» |
| `/dev-pipeline:frontend-design` | как сделать макеты не шаблонными: план, проверка на приметы ИИ-дизайна, самопроверка по скриншоту | подключает плагин; можно и вам: «сделай менее шаблонно» |
| `/dev-pipeline:web-design-guidelines` | правила интерфейса на уровне кода: доступность, фокус, формы, движение, тексты; по ним пишут и проверяют экраны | подключает плагин; можно и вам: «проверь интерфейс» |
